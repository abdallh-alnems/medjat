# Feature Specification: Rebuild Employee App — Phone + Activation Code Sign-In

**Feature Branch**: `001-rebuild-employee-app`
**Created**: 2026-05-31
**Status**: Draft
**Input**: User description: "Medjat is an HR product with two apps: the management app (medjat_central, already finished) and the employee app (medjat_app, still in progress). The employee app was built the wrong way — employees should sign in with their phone number and an activation code (not the current email/Google flow). Other capabilities will be added later. See REBUILD_PHONE_CODE_PLAN.md for details."

## Overview

The management side of the Medjat HR product is complete. Company administrators already create employees, capture their phone numbers, and generate short-lived activation codes. The employee-facing app, however, was built around an email / social sign-in flow that does not fit how the business actually onboards employees. Employees do not self-register; they are handed a phone number record and an activation code by their company's administration.

This feature rebuilds the employee app so that an employee signs in once with their **phone number + activation code**, then stays signed in on that device until their session is intentionally ended (by signing out or when administration re-issues their code). After sign-in the employee can use the existing employee capabilities — leave requests, attendance, payroll slips, personal profile/documents, and notifications — all tied to their own identity rather than to a separately registered account.

The app also offers a **Kiosk mode**: a phone can be paired (via an administration code) as a branch's shared "reception/upload" attendance device, where employees check in/out by face/fingerprint. This is a distinct device mode from an employee's personal phone-and-code experience.

## Clarifications

### Session 2026-05-31

- Q: After an employee signs out, the activation code is already consumed (FR-005). How does the employee sign back in? → A: A new activation code must be generated by administration; signing out permanently disconnects the device until administration issues a new code.
- Q: The session is persistent until revoked (FR-007). Should it auto-expire after an inactivity period for security? → A: No automatic expiry — the session stays active indefinitely until ended by sign-out or code re-issuance (no inactivity timeout).
- Q: Should the employee be able to edit their own profile? → A: No — the profile is view-only; all profile changes are made by administration.
- Q: Which leave types can an employee select (FR-014)? → A: Annual, Sick, Personal, and Unpaid.
- Q: What is the failed sign-in attempt limit before temporary blocking (FR-024)? → A: 10 failed attempts per hour per source IP address.

### Session 2026-06-01

> The following were grounded by reading the existing shared backend (`backend_medjet`), which already implements branches, attendance, and leaves for the management app and serves both apps. The employee app must conform to this existing behavior. (Only facts directly verified in the code are recorded here.)

- Q: Does attendance check-in enforce a branch geofence? → A: Yes — the backend validates the device's GPS against the branch and rejects an out-of-range check-in (error `GPS_OUT_OF_RANGE`). The allowed radius is configured per company. (confirmed in `attendance/check_in.php` via `GpsService::validateCheckIn`)
- Q: What does a check-in submit, and is it restricted to an assigned branch? → A: Check-in submits a `branch_id`, GPS coordinates, and an optional QR code (validated against that branch when provided); there is no assigned-branch restriction — an employee may check in at any branch in their company. (confirmed in `attendance/check_in.php`)
- Q: How is a leave request validated on submission? → A: The leave type must be one of Annual/Sick/Personal/Unpaid, and an overlapping leave for the same employee is rejected (`leave_overlap`, 409). No balance check is enforced at submission. (confirmed in `leaves/apply.php`)
- Q: What happens when an employee opens payroll for a month with no slip? → A: The month defaults to the current month; if no slip exists the backend returns not-found, so the app shows a "no slip available" state. (confirmed in `payroll/get_slip.php`)
- Q: How is offline attendance handled? → A: The app submits a batch of stored offline records to a sync endpoint when connectivity returns; offline attendance is gated by a company setting. (confirmed in `attendance/sync_offline.php` + offline-attendance setting)
- Q: How is Kiosk (shared attendance device) mode activated on a phone? → A: From the sign-in screen, by pairing the device with an administration-generated pairing code/QR for a branch (no employee login needed); the device then receives a long-lived station credential. (confirmed in `stations/create.php` + `station/activate.php`, `X-Station-Token`)
- Q: How do employees identify themselves when checking in at the Kiosk? → A: By face recognition and/or fingerprint, with administration choosing the method per branch (face only, fingerprint only, or both); the admin PIN is only for unlocking/enrolling, not for employee check-in. (confirmed in `station/check_in_out.php` method enum `face|fingerprint|both` + branch `station_methods` `face_only|fingerprint_only|both_available`)
- Q: Is the Kiosk device locked to the attendance screen? → A: Yes — it stays on the attendance screen, and exiting Kiosk mode or its settings requires the administration PIN. (confirmed in `station/verify_admin_pin.php` + station lock state)
- Q: Does the Kiosk support offline check-in? → A: Yes — check-ins are captured offline and synced when connectivity returns; the employee list and settings are fetched when online. (per `station/sync.php`)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Sign in with phone number and activation code (Priority: P1)

An employee receives their phone number and a 6-character activation code from their company's administration. They open the employee app, enter the phone number and the code, and are signed in to their personal home screen. They stay signed in across app restarts without re-entering anything.

**Why this priority**: This is the foundation. No other employee capability is usable without an authenticated session, and the entire reason for the rebuild is to replace the wrong sign-in model. It is the minimum viable product on its own — even with nothing else, a working, persistent sign-in is the core unlock.

**Independent Test**: Generate a valid code for a known employee from the management app, enter the matching phone number and code in the employee app, confirm the employee reaches the home screen, close and reopen the app, and confirm they remain signed in.

**Acceptance Scenarios**:

1. **Given** an employee with a valid, unused, unexpired activation code and a matching phone number, **When** they enter both in the app, **Then** they are signed in and taken to the home screen.
2. **Given** an employee who has already signed in on a device, **When** they close and reopen the app, **Then** they remain signed in without re-entering credentials.
3. **Given** an entered activation code that does not exist or has expired, **When** they attempt to sign in, **Then** sign-in is rejected with a clear "code invalid or expired" message and no session is created.
4. **Given** a valid activation code but a phone number that does not match the employee who owns that code, **When** they attempt to sign in, **Then** sign-in is rejected with a clear "phone number does not match the activation code" message.
5. **Given** a valid activation code, **When** sign-in succeeds, **Then** the employee's status becomes active and the activation code can no longer be reused.

---

### User Story 2 - Session ends when administration re-issues the code or the employee signs out (Priority: P1)

An employee is signed in on a device. When administration regenerates that employee's activation code, the existing device session is invalidated — on the next action the employee is returned to the sign-in screen. The employee can also deliberately sign out from the app's settings.

**Why this priority**: Session lifecycle is part of the core auth contract and a stated acceptance criterion. Administration must be able to cut off a lost/old device by re-issuing a code, and employees must be able to sign out. Without this the persistent-session model is unsafe.

**Independent Test**: Sign in successfully, regenerate the employee's code from the management app, perform any action in the employee app, and confirm the app returns the employee to the sign-in screen. Separately, tap sign-out and confirm the session is cleared.

**Acceptance Scenarios**:

1. **Given** a signed-in employee, **When** administration regenerates that employee's activation code, **Then** the employee's current device session is invalidated and the next protected action returns them to the sign-in screen.
2. **Given** a signed-in employee, **When** they choose "sign out", **Then** their session is ended and they are returned to the sign-in screen.
3. **Given** an employee whose session has been invalidated, **When** they attempt a protected action, **Then** they receive a clear "your session has expired, please sign in again" message rather than a silent failure.

---

### User Story 3 - Submit a leave request (Priority: P1)

A signed-in employee opens the leave section, sees their current leave balance, selects a leave type and dates, optionally enters a reason, and submits a leave request. The request reaches administration and the employee's managers are notified.

**Why this priority**: Leave request is the most important employee capability identified for this app (per the rebuild plan). It demonstrates the new authenticated session driving a real business workflow end-to-end and delivers immediate value to employees.

**Independent Test**: As a signed-in employee, view the leave balance, submit a valid leave request, and confirm it appears on the management side and that the relevant manager is notified.

**Acceptance Scenarios**:

1. **Given** a signed-in employee, **When** they open the leave section, **Then** they see their current leave balance.
2. **Given** a signed-in employee, **When** they submit a leave request with a valid type and date range, **Then** the request is recorded and visible to administration.
3. **Given** a submitted leave request, **When** it is created, **Then** the responsible manager receives a notification.
4. **Given** a requested date range that conflicts with an existing leave, **When** the employee submits, **Then** the request is rejected with a clear conflict message.

---

### User Story 4 - Record attendance with QR + location (Priority: P2)

A signed-in employee checks in and out of work by scanning a branch QR code with their device location captured. The home screen reflects today's attendance state (checked-in / checked-out). If the device is offline at the moment of check-in/out, the record is captured locally and synced when connectivity returns.

**Why this priority**: Attendance is a primary daily workflow, but the business value of the rebuild is first proven by sign-in and leave. Attendance builds directly on the authenticated session.

**Independent Test**: As a signed-in employee, scan a valid branch QR with location enabled, confirm check-in is recorded and reflected on the home screen, then check out. Repeat with the device offline and confirm the record syncs afterward.

**Acceptance Scenarios**:

1. **Given** a signed-in employee physically at any of their company's branches, **When** they submit a check-in for that branch with GPS location available, **Then** their check-in is recorded.
2. **Given** an employee who has checked in, **When** they later check out, **Then** the home screen shows the updated attendance state.
3. **Given** the device has no connectivity during check-in/out, **When** the employee performs the action, **Then** it is captured locally and submitted automatically once connectivity is restored.
4. **Given** a check-in attempt from outside the branch's allowed radius, **When** the employee submits it, **Then** the check-in is rejected with a clear "outside branch range" message.

---

### User Story 5 - View payroll slip (Priority: P2)

A signed-in employee selects a month and views their payroll slip for that period, and can download/open it as a document.

**Why this priority**: Payroll visibility is a valued self-service capability but is consumption-only and not on the critical onboarding path.

**Independent Test**: As a signed-in employee, select a month with an available slip, confirm the slip is displayed, and confirm it can be downloaded/opened.

**Acceptance Scenarios**:

1. **Given** a signed-in employee, **When** they select a month with an available payroll slip, **Then** the slip details are displayed.
2. **Given** a displayed payroll slip, **When** the employee chooses to download it, **Then** the slip is produced as a document they can open.

---

### User Story 6 - View personal profile, documents, and notifications (Priority: P3)

A signed-in employee views their own profile (name, job title, branch, leave balance) and their documents, and reads notifications (e.g., leave approvals, payroll) with the ability to mark them read.

**Why this priority**: Supporting self-service views that round out the experience. Valuable but lower urgency than the transactional flows above.

**Independent Test**: As a signed-in employee, open the profile and confirm correct personal details and documents are shown; open notifications, confirm relevant items appear, and mark one as read.

**Acceptance Scenarios**:

1. **Given** a signed-in employee, **When** they open their profile, **Then** they see their own personal details, leave balance, and documents in view-only form (no edit controls).
2. **Given** a signed-in employee with notifications, **When** they open the notifications list, **Then** they see their notifications and can mark items as read.
3. **Given** any signed-in employee action, **When** data is requested, **Then** only that employee's own data is returned (no other employee's data is accessible).

---

### User Story 7 - Kiosk (shared attendance device) mode (Priority: P3)

A company designates a phone as the branch's shared attendance device ("the reception/upload phone"). From the sign-in screen (no employee login needed), the device is paired using an administration-generated pairing code/QR for a branch. Once paired, the device stays locked on an attendance screen showing the branch's employees; each employee checks in/out by face recognition and/or fingerprint (the method is chosen by administration per branch). Leaving Kiosk mode requires the administration PIN.

**Why this priority**: This is a distinct, additive device mode layered on top of the core personal employee experience (US1–US6). It is independently valuable for branches that prefer a single shared check-in device, but the rebuild's primary deliverable is the personal phone-and-code experience, so it ranks after those.

**Independent Test**: Pair a spare phone using a pairing code generated from the management app, confirm the device shows the branch's employees and stays locked to the attendance screen, have an enrolled employee check in by face/fingerprint, and confirm the attendance is recorded; confirm exiting Kiosk mode requires the administration PIN.

**Acceptance Scenarios**:

1. **Given** a phone on the sign-in screen and a valid pairing code/QR from administration, **When** the operator pairs the device, **Then** the device enters Kiosk mode for that branch and shows the branch's active employees.
2. **Given** a paired Kiosk and an employee enrolled with face/fingerprint, **When** the employee verifies by the method enabled for the branch, **Then** their check-in or check-out is recorded and confirmed on screen.
3. **Given** a paired Kiosk, **When** someone attempts to leave Kiosk mode or open its settings, **Then** the administration PIN is required.
4. **Given** a Kiosk with no connectivity, **When** an employee checks in, **Then** the record is captured locally and synced once connectivity returns.
5. **Given** a Kiosk that is moved beyond the allowed distance from its branch, **When** it reports its location, **Then** it is locked and refuses check-ins until administration unlocks it.

### Edge Cases

- An activation code that is valid but belongs to a different company/tenant than expected — the code globally identifies the owning employee; the phone number serves as a second check.
- Phone number entered with spaces, dashes, or a leading "+" — input must be normalized so formatting differences do not cause a false "phone does not match" rejection.
- The same activation code entered twice — only the first successful sign-in consumes it; a second attempt is rejected as already used.
- An employee whose account has been terminated attempts to sign in or act — access is denied with a clear message.
- Repeated rapid sign-in attempts (e.g., guessing codes) — the system temporarily blocks the source IP after 10 failed attempts within an hour.
- The employee signs in on a new device while an old device session exists — the most recent successful sign-in is the active session for that employee; the prior device session is no longer valid.
- Notifications must continue to be delivered to the employee's device after the sign-in model changes (push delivery must not depend on the removed sign-in method).
- Employee checks in while outside the branch's allowed radius — check-in is rejected with a clear "outside branch range" message.
- Employee provides a QR code that does not match the selected branch — check-in is rejected with an "invalid QR for this branch" message.
- Employee submits a leave request that overlaps an existing leave — the request is rejected with a clear "overlapping leave" message.
- Employee opens payroll for a month with no slip — a friendly "no slip available for this month" state is shown.
- Kiosk pairing code/QR is invalid or expired — pairing is rejected with a clear message and the device stays on the sign-in screen.
- Employee with no biometric enrollment tries to check in at the Kiosk — they cannot be recognized; administration must enroll their face/fingerprint (admin-PIN gated) first.
- The same employee checks in again at the Kiosk within a short interval — the duplicate is rejected ("too soon").
- A Kiosk device is moved away from its branch or is locked by administration — it refuses check-ins and clearly shows its locked state until unlocked.
- Kiosk is offline — check-ins are queued locally and the employee list reflects the last successful sync.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Employees MUST be able to sign in using only their phone number and an administration-issued activation code; no email, password, or social sign-in is required or offered.
- **FR-002**: The system MUST reject sign-in when the activation code does not exist, has expired, or has already been used, with a clear, user-facing reason.
- **FR-003**: The system MUST reject sign-in when the provided phone number does not match the employee who owns the activation code, with a clear, user-facing reason.
- **FR-004**: The system MUST normalize phone numbers (ignoring spaces, dashes, and a leading "+") before comparing the entered phone number to the stored one.
- **FR-005**: On successful sign-in the system MUST mark the activation code as used so it cannot be reused; signing back in (after sign-out or session revocation) requires a new activation code generated by administration.
- **FR-006**: On successful sign-in the system MUST set the employee's status to active.
- **FR-007**: The system MUST issue a persistent, device-bound session on successful sign-in so the employee remains signed in across app restarts until the session is ended; the session MUST NOT auto-expire from inactivity and remains active indefinitely until ended by sign-out or activation-code re-issuance.
- **FR-008**: Each employee MUST have at most one active session at a time; a new successful sign-in MUST invalidate any prior active session for that employee.
- **FR-009**: The system MUST invalidate an employee's active session when administration regenerates that employee's activation code.
- **FR-010**: Employees MUST be able to sign out, which ends the current session and returns them to the sign-in screen; after sign-out the device stays disconnected until administration issues a new activation code (signing out is a deliberate, full disconnect, not a pause).
- **FR-011**: When a session has expired or been invalidated, the app MUST detect this on the next protected action, end the local session, and return the employee to the sign-in screen with a clear "session expired" message.
- **FR-012**: All employee data access MUST be scoped to the signed-in employee; an employee MUST NOT be able to access another employee's data.
- **FR-013**: Employees MUST be able to view their current leave balance (for the relevant year).
- **FR-014**: Employees MUST be able to submit a leave request specifying a leave type (one of: Annual, Sick, Personal, Unpaid) and date range (start and end date), with an optional reason.
- **FR-014a**: The system MUST reject a leave request that overlaps an existing leave for the same employee (conflict response).
- **FR-015**: When a leave request is submitted, the responsible manager MUST be notified.
- **FR-016**: Employees MUST be able to check in and check out by submitting the branch (identified by its branch ID, with an optional branch QR code validated when provided) together with captured device GPS location, and the app MUST reflect today's attendance state. There is no assigned-branch restriction — an employee may check in at any branch in their company. Check-in MUST be rejected when the device's location is outside the company-configured allowed radius for the branch (out-of-range response).
- **FR-017**: The app MUST capture attendance actions performed while offline and submit them (as a batch) to be synced automatically once connectivity is restored. Offline attendance applies only when the company permits offline attendance.
- **FR-018**: Employees MUST be able to view and download their payroll slip for a selected month (defaulting to the current month); when no slip exists for the selected month, the app MUST show a clear "no slip available" state rather than an error.
- **FR-019**: Employees MUST be able to view their own profile (including name, job title, branch, and leave balance) and their documents; the profile is view-only — employees MUST NOT edit their own profile data (all profile changes are made by administration).
- **FR-020**: Employees MUST be able to view their notifications and mark them as read.
- **FR-021**: The employee app MUST continue to receive push notifications after the sign-in model change; push delivery MUST NOT depend on the removed sign-in method.
- **FR-022**: The previous sign-in method (email / social / code-via-old-flow) MUST be removed from the employee app so it is no longer presented or usable.
- **FR-023**: The rebuild MUST NOT degrade or break the existing management app or its workflows.
- **FR-024**: The system MUST limit abusive repeated sign-in attempts (e.g., code guessing) by temporarily blocking a source IP address after 10 failed sign-in attempts within one hour.
- **FR-025**: The sign-in screen MUST guide the employee that the phone number and activation code are obtained from their company's administration.
- **FR-026**: The app MUST provide a Kiosk (shared attendance device) mode, accessible from the sign-in screen without an employee session, activated by pairing the device with an administration-generated pairing code/QR for a specific branch; on success the device MUST receive and securely store a long-lived station credential used for all subsequent kiosk requests.
- **FR-027**: In Kiosk mode the device MUST show the branch's active employees and allow each to check in/out, with identity verified by face recognition and/or fingerprint according to the method administration configured for that branch (face only, fingerprint only, or both).
- **FR-028**: Biometric matching MUST occur on the device; the Kiosk MUST honor the branch's configured confidence threshold and anti-spoofing setting, and MUST record each recognition attempt (success/failure) for audit.
- **FR-029**: The Kiosk MUST stay locked to the attendance screen; exiting Kiosk mode or opening its settings MUST require the administration PIN.
- **FR-030**: The Kiosk MUST support administration-gated enrollment of an employee's face/fingerprint on the device, requiring the administration PIN before enrollment.
- **FR-031**: The Kiosk MUST capture check-ins while offline and synchronize them when connectivity returns, and MUST refresh the branch employee list and settings when online.
- **FR-032**: The Kiosk MUST reject a duplicate check-in for the same employee within a short interval ("too soon").
- **FR-033**: The Kiosk MUST send periodic liveness/location heartbeats; if the device is moved beyond the allowed distance from its branch, or is locked by administration, it MUST refuse check-ins and clearly show its locked state until unlocked.

### Key Entities *(include if feature involves data)*

- **Employee**: A person who works for a company in the system. Key attributes: name, phone number (unique within their company), job title, branch, status (e.g., active / terminated), leave balance, and associated documents. The subject of every employee-app capability.
- **Activation Code**: A short, time-limited code issued by administration that identifies one specific employee. Attributes: the code value, expiry, used/unused state, and the employee it belongs to. Consumed on first successful sign-in.
- **Employee Session**: The persistent, device-bound proof that an employee is signed in on a given device. Attributes: the employee it belongs to, device information, issued time, last-used time, and active/ended state. At most one active session per employee.
- **Company (Tenant)**: The organization an employee belongs to; scopes employee records and phone-number uniqueness.
- **Branch**: A physical location of a company used for attendance (via its branch ID and optional QR code) and employee assignment. Has a company-configured allowed radius used to geofence check-in against the device's GPS location.
- **Leave Request**: An employee's request for time off, with a leave type (Annual, Sick, Personal, or Unpaid), date range (start/end date), optional reason, and status (e.g., pending); visible to administration and triggering manager notification.
- **Leave Balance**: The employee's leave balance figures for the relevant year.
- **Attendance Record**: A check-in or check-out event with associated branch, location (GPS), and time; may be captured offline and synced later. Kiosk-originated records also reference the station and the verification method (face/fingerprint).
- **Attendance Station (Kiosk)**: A device paired to a branch to act as a shared attendance terminal. Attributes: device name, the branch it serves, a long-lived station credential, lock state and reason, last heartbeat/sync time, and last known location. Identity-verification methods and thresholds are inherited from the branch's station settings.
- **Biometric Enrollment**: An employee's enrolled face and/or fingerprint data and enrollment status, used by the Kiosk to recognize the employee at check-in. Enrolled on the Kiosk under administration-PIN control.
- **Payroll Slip**: A monthly statement of an employee's pay, viewable and downloadable by the employee.
- **Notification**: A message delivered to an employee (e.g., leave decision, payroll), with a read/unread state.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: An employee given a valid phone number and activation code can complete sign-in and reach the home screen in under 60 seconds on first attempt.
- **SC-002**: 100% of sign-in attempts with an invalid/expired code, or a phone number that does not match the code, are rejected with a clear reason and create no session.
- **SC-003**: After a successful sign-in, the employee remains signed in indefinitely without re-entering credentials and with no inactivity timeout, until the session is ended by sign-out or code re-issuance.
- **SC-004**: When administration regenerates an employee's code, that employee's app returns to the sign-in screen on the very next protected action (no continued access on the old session).
- **SC-005**: An employee can submit a valid leave request in under 90 seconds, and the request and its manager notification are observable on the management side.
- **SC-006**: Attendance actions taken while offline are 100% reconciled (no lost records) once connectivity returns.
- **SC-007**: No employee can retrieve another employee's data through any employee-app capability (verified across leave, attendance, payroll, profile, documents, and notifications).
- **SC-008**: The management app's existing workflows show no regressions attributable to this change.
- **SC-009**: Employees continue to receive push notifications (e.g., leave decisions) after the change, with delivery success comparable to before the change.
- **SC-010**: The employee app presents no email/social/old sign-in option anywhere in the experience.
- **SC-011**: A spare phone can be paired into Kiosk mode for a branch in under 2 minutes using an administration pairing code, after which an enrolled employee can check in by the branch's configured biometric method in under 10 seconds.
- **SC-012**: Kiosk mode cannot be exited without the administration PIN, and a Kiosk moved out of its allowed branch range stops accepting check-ins.

## Assumptions

- The management app already supports creating employees with phone numbers and generating activation codes; no new management-side capability is required beyond ensuring the code and phone are communicated to the employee.
- Activation codes are unique enough to globally identify the owning employee, while phone numbers are unique only within a company; therefore the code identifies the employee and the phone number is a secondary verification.
- Push notification, crash reporting, and analytics capabilities are retained; only the previous sign-in mechanism is being removed.
- Employees receive their phone number and activation code through an out-of-band channel (handed over by administration); the app does not send codes itself.
- A single device per employee at a time is acceptable; signing in on a new device supersedes the previous device's session.
- "Other capabilities to be added later" mentioned by the project owner are out of scope for this feature; this feature covers the sign-in rebuild and reconnecting the already-present employee capabilities (leave, attendance, payroll, profile/documents, notifications).
- The user interface remains Arabic (right-to-left), consistent with the existing apps.
- The backend serving both apps already contains the data structures needed for device-bound sessions and activation codes.
- Company-level rules — geofence radius, whether offline attendance is allowed, and station settings (enabled methods, confidence threshold, anti-spoofing, admin PIN, allowed distance) — are configured in the existing backend; the employee app consumes and honors these settings rather than hard-coding them.
- Kiosk (station) attendance is a distinct device mode from the personal QR + GPS check-in (US4) and reuses the existing backend station endpoints; both modes ship in this feature.
- Personal employee check-in (US4) uses QR + GPS, while Kiosk check-in (US7) uses on-device face/fingerprint biometrics — these are intentionally different verification paths.

## Out of Scope

- Self-service employee registration or account creation by employees.
- Employees editing their own profile data (profile is view-only on the employee app; changes are made by administration).
- New employee capabilities beyond those already present in the app and the Kiosk mode (US7) added here (further capabilities to be specified separately later).
- Building station management on the administration side (creating stations, generating pairing codes, setting station options) — this already exists in the management app; the employee app only consumes it.
- Changes to how administration creates employees or generates codes, beyond ensuring the code/phone are available to hand to employees.
- Multi-device concurrent sessions for a single employee.
- Replacing or changing push notification, analytics, or crash-reporting providers.
